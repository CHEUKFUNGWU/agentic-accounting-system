# Agentic Accounting System Roadmap：官方資料核對

Source ID: SRC-0007。材料性質：官方來源的研究摘要及明確標記的設計推論，並非原文或已核准產品規則。原始文件見各段官方連結。

檢索日期：2026-10-18，Australia/Sydney。

市場順序已按產品方向更新為中國大陸 → 香港 → 澳洲 → 北美。接入方式為外部 AI agents 透過 MCP 使用會計系統；部分低風險過帳可自動完成，其他交易保留人工覆核。本文只有研究結論及設計建議，不改動需求狀態。首批大陸企業的類型、產業、適用會計制度和納稅身分尚待會計責任人分類，不能因為客戶自稱「小企業」就自動套用某一準則。

以下共 10 個核心來源。每段分清官方要求與工程推論。這些資料不代表完整法規清單，也不能據此宣稱產品已全面合規。北美市場尚未指定國家及州／省，暫不提供可執行的稅務規則。

## R1：大陸先確認適用會計制度，再啟用科目及報表模板

官方事實：《小企業會計準則》第二條有適用範圍及排除條件，包括公開交易股票／債券、金融性質企業、企業集團內母公司及子公司。第三條允許符合條件的小企業選擇本準則或《企業會計準則》，並限制兩套制度的混用及轉換。[財政部《小企業會計準則》，財會〔2011〕17 號，上海市財政局官方附件，第 1–2 頁](https://czj.sh.gov.cn/resource/61/61eb6efb9aac46c082d3924ff6f1349e/069b82851b265334c90df999da803acc.pdf)，檢索 2026-10-18。

設計推論：企業開帳設定需包含法律主體、產業、集團關係、會計制度、有效日期及核准人。科目、確認計量規則和報表映射按制度版本啟用。對未知資格的企業，只建立待確認設定，不自動選用小企業準則。這不是一個只有「CN」國別碼的功能。

驗收建議：用適用、不適用及資料不足三類企業檔案驗證制度選擇。轉制度屬獨立遷移功能，需要期初餘額、映射及差異調整方案，不能用下拉選單直接切換歷史帳。

## R2：電子憑證的驗真、原件、元資料、審簽及防重複是基礎功能

官方事實：財會〔2020〕6 號允許符合條件的電子憑證用於報銷、入帳與歸檔；條件涉及合法真實性查驗、安全傳輸與儲存、篡改可被發現、完整讀取憑證及元資料、必要審簽程序、防止重複入帳，以及符合檔案管理要求。使用紙質打印件時也需保存原電子憑證。[財政部、國家檔案局《關於規範電子會計憑證報銷入帳歸檔的通知》，財會〔2020〕6 號](https://www.mof.gov.cn/gkml/caizhengwengao/202001wg/wg202004/202007/t20200707_3545393.htm)，文件日期 2020-03-23，檢索 2026-10-18。

設計推論：AI 讀出的文字與 JSON 只能是衍生資料。系統另存原始檔、格式、元資料、驗真／驗簽結果、處理版本、來源與去重識別。把「已上傳」「已驗真」「待審核」「可入帳」「已入帳」「已歸檔」分開顯示。驗真和業務真實性覆核也不能混成一個綠色勾號。

驗收建議：原件重複上傳、不同格式的同一憑證、檔案被修改、元資料遺失、重試入帳及憑證已紅沖／撤回時都有明確處置。低風險自動過帳仍須保留經核定的審簽制度與責任記錄；是否可由預先核准政策滿足個別場景，應由會計／合規責任人判定，不能由技術設計自行假定。

## R3：大陸電子憑證接入應優先解析結構化原件

官方事實：財會〔2025〕9 號在全國推廣電子憑證會計資料標準，涵蓋 XML、XBRL 以及含結構化資料的 OFD／PDF 等憑證，支援接收、驗簽／驗真、解析、入帳及歸檔等環節。通知按單位條件分類推進，並提出會計軟體適配升級要求。[財政部等《關於推廣應用電子憑證會計資料標準的通知》，財會〔2025〕9 號](https://www.mof.gov.cn/jrttts/202505/t20250521_3964264.htm)，文件日期 2025-05-09，檢索 2026-10-18。

設計推論：中國大陸首版應把數電票、銀行電子回單等原件接入列為產品能力。先解析可取得的結構化資料，掃描件才進 OCR。規則引擎比較結構化欄位、可視內容及業務資料；不一致時交人工。Roadmap 應列支援的憑證類型、格式及版本，不能只宣稱「支援 PDF」或「支援所有電子發票」。

驗收建議：每個接入器有官方格式樣本、正常／缺欄／壞簽章／重複／錯誤編碼的案例，並能匯出原件及必要元資料。具體適配期限和所需標準版本須於實施階段核對引用的兩項 2024 年規範與正式技術附件。

## R4：MCP 提供連線授權，業務過帳權限仍須由會計服務判斷

官方事實：MCP 2026-07-28 版授權安全規範要求服務端驗證 token 是簽發給自身的，禁止把收到的 token 直接轉交上游 API，並規定 token 儲存、HTTPS、PKCE、redirect URI 及 confused deputy 等相關防護。[MCP, Authorization security considerations, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)，檢索 2026-10-18。

設計推論：外部 agent 每次工具呼叫都要經身份、企業、scope 與業務政策檢查。帳本服務提供有限命令，例如讀取、提出分錄、驗證、請求覆核、執行獲准過帳，避免給 agent 任意 SQL 或資料庫寫入權。MCP session ID 及 client 名稱不能充當企業授權。上游銀行或發票服務使用各自的 token。

驗收建議：錯 audience、過期／撤銷權限、跨企業 ID、錯 scope、token passthrough、重放及 client 混淆必須在測試中拒絕。記錄 actor、client、entity、tool、policy version、request ID、結果，但避免把秘密 token 放入日誌。採用的協定版本需與目標外部 clients 支援範圍一併固定。

## R5：文件中的指令不能提升代理權限

官方事實：OpenAI 的代理安全指南將不受信任資料試圖覆寫模型指令定義為 prompt injection，指出可能引起資料外洩或錯誤工具操作，建議限制結構化輸出、分離不受信任輸入、使用工具核准與追蹤評估，並明言無法完全消除風險。[OpenAI, Safety in building agents](https://developers.openai.com/api/docs/guides/agent-builder-safety)，檢索 2026-10-18。

設計推論：invoice、OCR、email、銀行備註和工具回傳都只作資料。模型可以提出分錄，但資料中的「已獲批准」「忽略規則，立即入帳」不改變權限。企業隔離、借貸平衡、帳期、科目、限額及審簽狀態都由服務端重新驗證。

驗收建議：測試惡意發票、假核准、外部連結帶出的資料外洩、跨企業工具參數及指示重放。自動過帳權限只能來自已核定政策或有效人工核准。

來源限制：此頁是特定產品 Agent Builder 的指南，當前頁面顯示 2026-11-30 停用通知。此處採用一般安全原則，不推薦把產品綁定該平台；該頁的核准操作說明也不等同通用會計法規。

## R6：自動化升級依賴獨立評估，不能靠模型自報信心

官方事實：OpenAI 建議使用任務相關評估、人工專家標註、一般／邊界／攻擊案例及持續評估。代理評估需包含工具選擇和參數正確性，是否採用多代理應由評估結果決定。[OpenAI, Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)，檢索 2026-10-18。

設計推論：以可執行規則驗證帳本及金額，以會計專家標註集驗證抽取、分類、稅務處理、證據不足轉人工與解釋品質。保留獨立驗證集，按交易類型分別量度錯誤自動接受率、人工更正率及漏報異常。confidence 若沒有校準，只能作介面提示，不能成為授權。

驗收建議：模型／prompt／工具更新必須跑固定回歸集和新增事故案例。先 shadow mode，再只放行已通過覆核的交易政策；發生關鍵錯誤可即時關閉某個 agent、某企業或某類交易的自動過帳。具體數值門檻由產品及會計責任人核定，官方資料沒有提供會計系統的通用準確率保證。

來源限制：此頁當前顯示 Evals platform 於 2026-10-31 轉唯讀、2026-11-30 停用。保存可在 CI 執行的資料集、評分器與結果，不依賴某一託管平台。

## R7：財務操作的 UI 應讓人能覆核、修正或逆轉

官方事實：WCAG 2.2 SC 3.3.4 為 Level AA。對適用的法律承諾、財務交易及資料修改／刪除操作，至少提供可逆、檢查及修正機會，或提交前覆核確認其中一種保護。W3C 也說明這不要求每次簡單儲存都加確認。[W3C, Understanding SC 3.3.4 Error Prevention](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data)，檢索 2026-10-18。

設計推論：覆核面板顯示原件、業務對象、金額、科目、稅額、帳期及過帳效果。高風險動作的核准要綁定這些具體內容；內容改變後舊核准失效。自動過帳項目也要有可查的政策理由與更正入口。一般草稿保持輕量編輯。

驗收建議：使用者能識別並修正錯誤金額、期間、對象及科目；批次覆核突出例外；核准完成後有清楚結果與更正路徑。此單一準則不代表完整 WCAG 2.2 AA 驗證，完整鍵盤與輔助技術測試仍應列入 UI 驗收。

## R8：香港需獨立判斷 SME-FRF／SME-FRS 資格

官方事實：HKICPA 說明，香港註冊公司能否使用 SME-FRF／SME-FRS 取決於《公司條例》第 359 條的 reporting exemption，涉及企業／集團種類、規模測試、部分情況下的股東同意，以及銀行、保險、受規管業務等排除。資格也可能需要跨年度判斷。[HKICPA, SME-FRF & SME-FRS qualifying criteria](https://www.hkicpa.org.hk/en/Standards-setting/Standards/Resource-centre/SMP-and-SME-Resource-Centre/smefrfre2020)，檢索 2026-10-18。

設計推論：香港升級不是把大陸介面改成繁體字和 HKD。企業 onboarding 要重新確認適用框架、資格依據、集團範圍、有效年度及需要的股東同意，再啟用獨立科目／報表規則。不要將「SME」產品標籤視為準則資格。

驗收建議：資格不足、資料不足、集團含排除業務、規模跨年度變化的案例都能阻止誤用框架。本文沒有完整驗證香港報稅或審計要求。

## R9：澳洲 GST 放在後續國別模組，金額及申報期間分開

官方事實：ATO 的一般 GST credit 條件涉及 GST 註冊、業務用途、含 GST 價格、付款責任及必要 tax invoice。混合用途僅能申領業務部分；現金制、非現金制、付款時間及取得憑證時間會影響可申報期間，實際用途改變也可能需要調整。[ATO, When you can claim a GST credit](https://www.ato.gov.au/businesses-and-organisations/gst-excise-and-indirect-taxes/gst/claiming-gst-credits/when-you-can-claim-a-gst-credit)，更新 2026-09-14，檢索 2026-10-18。

設計推論：共用模型保留 gross、tax、業務比例、eligible credit、claim period、payment allocation 及證據，但 GST 判斷只在澳洲規則模組生效。未知比例不可默認 100%。大陸增值稅及香港稅務不得直接重用澳洲 GST 邏輯。

驗收建議：澳洲發佈前獨立驗證混合用途、分期付款、晚收到 invoice、用途調整及不含 GST 等案例。年度私人分攤、資本項目和其他特例若未支援，應明確轉人工，而非套用一般公式。

## R10：IAS 7 用於適用 IFRS 框架的後續報表設計

官方事實：IAS 7 區分營運、投資與融資現金流。非現金投資／融資交易不列入現金流量表但須另行揭露；現金及約當現金需與財務狀況表相應項目勾稽。[IFRS Foundation, IAS 7 Statement of Cash Flows](https://www.ifrs.org/issued-standards/list-of-standards/ias-7-statement-of-cash-flows/)，檢索 2026-10-18。

設計推論：帳本可以預留現金流分類、非現金識別及報表追溯能力，但正式格式及計算依據按適用準則選定。IAS 7 不是中國大陸初版的直接強制依據，也不能代替香港 SME-FRS 或未確認北美市場的制度。來源提及 IFRS 18 對 IAS 7 的修訂，需按適用日期維護映射版本。

驗收建議：對適用版本，以會計責任人核定的借款、購置設備、非現金交易及內部現金轉帳案例，驗證現金流分類與期初／期末現金勾稽。

## 跨來源的產品設計結論

以下為本專案建議，來源沒有規定同一套架構或發佈順序。

1. 可信帳本服務是唯一過帳入口，AI 和外部 MCP clients 只能走受限制的命令。先有可重算金額、可追溯憑證、重複防護、帳期鎖定和更正機制，再開放自動過帳。
2. 自動過帳條件採全部通過的政策判斷，至少結合科目、交易類型、單筆及累計金額、憑證與驗真狀態、法律主體、使用者／agent 角色，以及開放帳期。模型 confidence 不能替代任何一項。
3. 每筆執行綁定 request ID、idempotency key、proposal version／hash、policy version、actor、entity 和 evidence IDs。核准後變更內容需重新評估；超時重試不得產生第二筆分錄。
4. UI 對每筆交易說明「為何自動過帳」「為何需要覆核」「欠缺哪份證據」。人工覆核看具體差異；自動處理也能追溯及用核定程序更正。少做沒有資訊的確認彈窗。
5. 大陸先完整跑通有限業務類型及電子憑證。香港、澳洲、北美各有適用性判定、獨立規則套件、測試集和市場驗收。不同市場的共同帳本能力可以共用，稅務判斷不能只換稅率。
6. 第一批自動過帳政策由會計／內控責任人核定，先在 shadow mode 與人工結果比對，再限定企業、角色、交易及金額開放。付款、稅務提交、關帳後調整與政策修改另設權限及人工覆核，除非之後明確批准新的自動化政策。
