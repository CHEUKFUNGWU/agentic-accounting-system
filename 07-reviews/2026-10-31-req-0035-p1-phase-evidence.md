## Interpretations and residual notes for the owner

1. `ledger/fiscal.go AggregatePeriodState` maps fiscal_periods statuses FUTURE→open-for-projection and HARD_CLOSE→settled (least-settled wins; unknown status fails closed). SRC-0027 names the frequency limits and fiscal anchoring; the per-status mapping is engineering inference. Confirm or adjust.
2. BL-30's "warn on near-duplicates" residual: lookup normalization is trim + Unicode case-fold; near-duplicate warning is a caller concern not yet built (no caller exists before P4/P5).
3. BL-22's verification strength is offline-shape only (documented); live registry verification (Golden Tax, ATO, VIES) is I/O for a later phase.
4. The Python reference has no solo-mode exception in sod_guard (stricter than SRC-0028): the port keeps golden parity for the reference behaviour and implements the owner-decided rule as new functions (`SoloMode`, `CheckSelfApproval`). P4 wires the decided rule into the enforcement wall.
5. BL-36's per-entity-and-period unique constraint and in-transaction allocation are P2 store work per the ADR mapping; the pure rules (draft ID separation, neutral format, gap report) are P1-complete.
6. The workflow golden-fixture surface is small (45 cases) because every journal-producing Python path converts amounts through float64 (BL-27) — no posting success could be fixture'd without encoding the defect; the finding regressions carry the module's test weight.
7. Div at the parse-legal exponent extremes: subnormal-band results are kept (`1E-999999/1E+21 → 1E-1000020`), zero quotients clamp, overflow traps — fixture-pinned; inputs beyond Parse's ±999999 exponent scope remain rejected (documented P0 deviation).
